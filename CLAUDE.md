# LiteLLM Operator — Claude Code Instructions

## Project Identity

A standalone Kubernetes operator for deploying and managing production-ready LiteLLM AI Gateway instances. Built with the Operator SDK (which wraps kubebuilder and controller-runtime) for OLM integration, OperatorHub distribution, and first-class OpenShift support. Replaces the community Helm chart with a declarative, reconciliation-based approach that solves the Admin UI vs GitOps configuration conflict.

- **Repository:** `PalenaAI/litellm-operator`
- **Language:** Go 1.22+
- **Framework:** Operator SDK v1.38+ (kubebuilder v4, controller-runtime v0.18+)
- **License:** Apache 2.0
- **API Group:** `litellm.palena.ai`
- **API Version:** `v1alpha1`
- **Distribution:** OLM bundles (OperatorHub, OpenShift Catalog) + Helm chart

## Coding Conventions

### Go Style

- Follow the standard Go project layout and Operator SDK / kubebuilder conventions
- Use `controller-runtime` idioms: `client.Client`, `ctrl.Result`, `ctrl.Request`
- All exported types must have godoc comments
- Use `logr` for structured logging (from controller-runtime), never `fmt.Println` or `log`
- Use constants for annotation keys, label keys, finalizer names
- Error wrapping: use `fmt.Errorf("context: %w", err)` — never naked errors

### Naming Conventions

```go
// CRD type files: lowercase singular
litellminstance_types.go
litellmmodel_types.go

// Controller files: match CRD name
litellminstance_controller.go

// Constants: PascalCase with prefix
const (
    FinalizerName       = "litellm.palena.ai/finalizer"
    AnnotationManagedBy = "litellm.palena.ai/managed-by"
    AnnotationSyncHash  = "litellm.palena.ai/sync-hash"
    LabelInstanceName   = "litellm.palena.ai/instance"
    LabelResourceType   = "litellm.palena.ai/resource-type"
)

// Status conditions: use standard condition types
const (
    ConditionReady        = "Ready"
    ConditionDatabaseReady = "DatabaseReady"
    ConditionRedisReady    = "RedisReady"
    ConditionConfigSynced  = "ConfigSynced"
)
```

### Reconciliation Patterns

Every controller must follow this pattern:

```go
func (r *LiteLLMModelReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    log := log.FromContext(ctx)

    // 1. Fetch the CR
    var model litellmv1alpha1.LiteLLMModel
    if err := r.Get(ctx, req.NamespacedName, &model); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    // 2. Handle deletion (finalizer pattern)
    if !model.DeletionTimestamp.IsZero() {
        return r.handleDeletion(ctx, &model)
    }

    // 3. Ensure finalizer
    if !controllerutil.ContainsFinalizer(&model, FinalizerName) {
        controllerutil.AddFinalizer(&model, FinalizerName)
        if err := r.Update(ctx, &model); err != nil {
            return ctrl.Result{}, err
        }
    }

    // 4. Resolve instanceRef → get LiteLLM endpoint + master key
    instance, err := r.resolveInstance(ctx, model.Namespace, model.Spec.InstanceRef)
    if err != nil {
        return ctrl.Result{RequeueAfter: 30 * time.Second}, err
    }

    // 5. Reconcile the resource against LiteLLM API
    result, err := r.reconcileModel(ctx, &model, instance)

    // 6. Update status
    if statusErr := r.Status().Update(ctx, &model); statusErr != nil {
        log.Error(statusErr, "failed to update status")
    }

    return result, err
}
```

### Error Handling

- Transient errors (network, API 5xx): `return ctrl.Result{RequeueAfter: 30 * time.Second}, nil`
- Permanent errors (invalid spec, 400): set status condition, don't requeue
- Always update status conditions on both success and failure
- Use `meta.SetStatusCondition()` for condition management

### Status Conditions

Use `metav1.Condition` with these standard fields:

```go
meta.SetStatusCondition(&instance.Status.Conditions, metav1.Condition{
    Type:               ConditionReady,
    Status:             metav1.ConditionTrue,
    Reason:             "AllResourcesReady",
    Message:            "All managed resources are ready",
    ObservedGeneration: instance.Generation,
})
```

### Secret Handling

- Never log secret values
- Always read secrets via `client.Get()` with the `SecretRef` pattern
- Store generated secrets (virtual keys, SCIM tokens) in operator-created Secrets
- Set `ownerReferences` on created Secrets so they are garbage collected

### Testing

- Unit tests: test individual functions, resource generation, diff logic
- Integration tests: use `envtest` (controller-runtime's test environment)
- E2E tests: test against a real cluster with a real LiteLLM instance
- Mock the LiteLLM API client interface for unit/integration tests
- Every controller must have tests for: create, update, delete, error recovery

## Key Design Decisions

### 1. Bidirectional Config Sync

The operator's killer feature. Every `syncInterval` (default 30s), the config sync controller:
1. Reads desired state from all CRDs referencing an instance
2. Reads actual state from LiteLLM API
3. Computes diff
4. Applies changes via LiteLLM API
5. Updates CRD statuses

Three policies for unmanaged resources (found in API but not in CRDs):
- `preserve` (default): leave them alone
- `prune`: delete them
- `adopt`: report in status as unmanaged

### 2. Member Management in LiteLLMTeam

Teams have a `memberManagement` field controlling who owns membership:
- `crd`: CRD is authoritative. Reconciler syncs members exactly as listed.
- `sso`: IdP is authoritative. Operator never touches members. Status reports SSO members.
- `mixed` (default): CRD members are additive. SSO members are preserved. Operator tracks which members it manages via `status.crdMembers`.

This prevents the operator from destroying SSO-provisioned memberships when `spec.members` is empty.

### 3. SSO/SCIM Configuration

SSO and SCIM are configured in `LiteLLMInstance.spec.sso` and `LiteLLMInstance.spec.scim`. The operator translates these into environment variables and config entries. The IdP is the source of truth for user identity — the operator manages infrastructure, not identity.

### 4. LiteLLMUser CRD

A secondary CRD for non-SSO environments. When SSO/SCIM handles user provisioning, `LiteLLMUser` CRDs are typically not needed. Useful for:
- Service accounts
- Bot users
- Environments without an IdP
- Declarative user management via GitOps

### 5. VirtualKey Secret Management

When a `LiteLLMVirtualKey` is created, the operator calls `POST /key/generate` and stores the returned API key in a Kubernetes Secret. The Secret name is recorded in `.status.keySecretRef` and pinned there, so editing `spec.keySecretName` afterwards cannot orphan the key material. The operator sets `ownerReferences` so the Secret is garbage collected when the VirtualKey CR is deleted — including on a Secret a user pre-created by hand, which is adopted rather than left unowned.

The Secret is reconciled on every pass, not only at mint time: `spec.keySecretTemplate.annotations` / `.labels` are merged onto it (operator labels win on conflict; entries added by other controllers are preserved), and both `keySecretName` and `keySecretTemplate` are excluded from the sync hash so Kubernetes-side edits never trigger a `POST /key/update`. LiteLLM stores only a hash of the key, so if the Secret is deleted the material is unrecoverable: the operator deletes the orphaned key, mints a replacement and emits a `KeySecretMissing` warning event. Absence is confirmed with an uncached read (`APIReader`) so a stale informer cache cannot rotate a working key.

## Current Feature Coverage (v0.11.3)

### Fully Implemented and Working

#### LiteLLMInstance (infrastructure)

- Deployment with rolling/recreate strategy, container security context, health probes
- ConfigMap generation (`proxy_server_config.yaml`) with general_settings, router_settings, litellm_settings
- Service (ClusterIP/NodePort/LoadBalancer), ServiceAccount
- Auto-generate master key and salt key Secrets
- Database: external connection via Secret, CloudNativePG integration (reads `{clusterName}-app` Secret)
- Database migration Job — runs `prisma migrate deploy` (applying LiteLLM's versioned migrations in `litellm-proxy-extras/migrations`) inside the gateway image by default. Set `spec.database.migration.useDatabaseImage: true` to run LiteLLM's dedicated `ghcr.io/berriai/litellm-migrations` image alone instead (recommended for v1.86+ — that image's entrypoint wraps `prisma migrate deploy` with P3005 baseline / P3009/P3018 idempotent recovery and the v2 migration resolver). Override the database image repo/tag via `spec.database.migration.databaseImage`. Job name is unique per (image, command) so toggling the mode triggers a fresh Job
- Redis configuration (host/port/password/URL via env vars)
- Ingress (standard k8s), OpenShift Route (unstructured), Gateway API HTTPRoute
- HPA v2 (CPU/memory metrics), PDB, NetworkPolicy (ingress-only on port 4000)
- TopologySpreadConstraints pass-through (proxy Deployment only)
- Pod scheduling via `spec.podScheduling` (`nodeSelector`, `tolerations`, `affinity`) applied to BOTH the proxy Deployment and the database migration Job. A Job's pod template is immutable, so placement is folded into the migration Job's name seed — changing it creates a fresh Job rather than leaving a pending one pinned to an unschedulable template. The seed is gated on placement *content*, not on the pointer, so an omitted `podScheduling`, an explicit `{}` and empty maps all yield the same Job name and do not re-run the migration
- Extra env vars and env-from injection. `spec.extraEnvVars` entries override operator-set env vars of the same name (deduped in place, user value wins) — primary use case is overriding `PROXY_BASE_URL` when exposing the gateway via Route/HTTPRoute/external LB instead of plain Ingress
- Callbacks (success_callback / failure_callback in config + env vars)
- Fallback chains: defaultFallbacks, per-model modelFallbacks, contentPolicyFallbacks, contextWindowFallbacks, maxFallbacks; retry policies (retryPolicy, modelGroupRetryPolicy) per error type
- Tag-based routing: `enableTagFiltering` and `tagFilteringMatchAny` in routerSettings; tags on LiteLLMModel (passed as `litellm_params.tags` in API calls); tags on LiteLLMTeam (team-tag association via API)
- Response caching: 6 backends (redis, redis-semantic, s3, gcs, qdrant, local) with TTL, namespace isolation, call-type filtering, default-off mode. Redis reuse from instance `spec.redis` when `caching.redis` is omitted. Credentials injected as env vars via Secret references
- Advanced budget controls: global proxy budget (`maxBudget`, `budgetDuration`), `globalMaxParallelRequests`, budget rescheduler tuning (`budgetReschedulerMinTime/MaxTime`) in generalSettings; `defaultMaxParallelRequests` and `providerBudgetConfig` (per-provider spending caps with time periods) in routerSettings — all written to `proxy_server_config.yaml`
- SSO (azure-entra/okta/google/generic-oidc) — client ID/secret, tenant, OIDC endpoints, scopes, user attribute mappings, default user/team params. `spec.sso.logoutUrl` wired to the `PROXY_LOGOUT_URL` env var. `spec.sso.customSsoHandler` supports two modes: `module` (dotted Python path to a handler in a pre-baked image) or `configMapRef` (operator mounts the ConfigMap at `/app/custom_sso_handlers/` and writes `general_settings.custom_sso: custom_sso_handlers.<stem>.<functionName>`). `spec.sso.defaultUserParams.teams` emitted under `default_internal_user_params.teams` (maps `teamId`/`role`/`maxBudgetInTeam` → `team_id`/`user_role`/`max_budget_in_team`) for auto-enrollment of new SSO users
- SCIM (enabled flag, token via Secret or auto-generated)
- Observability: ServiceMonitor (Prometheus), PrometheusRule (6 built-in alerts with per-alert suppression), Grafana dashboard ConfigMap
- CloudNativePG ScheduledBackup (snapshot/barmanObjectStore)
- Auto-rollback on ProgressDeadlineExceeded (tracks last successful revision)
- Config changes roll the proxy: the pod template carries `litellm.palena.ai/config-hash`, a digest of the *contents* of every ConfigMap the pod consumes (`configMapKeyRef` env vars, `envFrom`, ConfigMap and projected volumes). litellm parses `proxy_server_config.yaml` once at startup — it does not watch the file and has no reload endpoint for it — so without the digest a config-only change rewrites the ConfigMap while the rendered Deployment stays byte-identical, and the running gateway keeps its original config forever. This is what let a deleted `LiteLLMGuardrail` go on being enforced (a guardrail with an `apiKeySecretRef`/`envVars` happened to roll because its env var disappeared with it; one without did not), and it applied equally to `routerSettings`, fallbacks, caching, `rbac`, JWT claim mappings and every other config-only field. Also covers the custom SSO handler and Admin UI colour-theme ConfigMaps. Only projected keys are hashed; an absent ConfigMap hashes distinctly from a present one; a transient read failure is a reconcile error, never "the ConfigMap is gone". Operator-managed and re-derived each pass, so excluded from `preserveExternalPodTemplateAnnotations`
- Secret rotation rolls the proxy: the pod template carries `litellm.palena.ai/secret-hash`, a digest of the *contents* of every Secret the pod consumes (`secretKeyRef` env vars, `envFrom`, Secret and projected volumes). `secretKeyRef` values are resolved at container start and never refreshed, so without the digest a rotated Secret leaves the Deployment byte-identical and the running pod keeps the old value forever — this is what made an updated `LITELLM_LICENSE` never take effect. Only referenced keys are hashed (an unrelated key in a shared Secret does not restart the pod); `imagePullSecrets` are excluded (the kubelet reads them at pull time); an absent Secret hashes distinctly from a present one, so installing a license later also rolls. A transient read failure is returned as a reconcile error, never treated as "the Secret is gone". The digest is operator-managed and re-derived each pass, so it is excluded from `preserveExternalPodTemplateAnnotations` while `kubectl.kubernetes.io/restartedAt` is still preserved alongside it
- Pod-level fault reporting: when the workload is not ready the controller inspects the instance's pods and surfaces the cause on the CR — a `PodsHealthy` condition (independent of `Ready`) plus `.status.unhealthyPods[]` (`name`, `phase`, `reason`, truncated `message`, `restartCount`), capped at 3. Recognizes CrashLoopBackOff (reporting the *previous* termination's exit code, not back-off timing), ImagePullBackOff, OOMKilled, CreateContainerConfigError, and Unschedulable. Pods are listed only while not ready (no extra reads when healthy, no pod watch); a Warning event fires only when the cause changes, so crash loops don't spam events. Requires pod `get;list;watch` RBAC
- Security: `runAsNonRoot` mode (switches to non-root image, sets security context); IP allowlisting (`spec.security.ipAllowlist`) with allowed IPs/CIDRs, `useXForwardedFor`, max request/response size limits — written to `general_settings`
- RBAC: `spec.rbac` with `enforce_rbac`, `admin_only_routes`, `allowed_routes`, `default_team_disabled`, `key_generation_settings` (enterprise), `role_permissions` (enterprise) — all written to `general_settings`
- Namespace-scoped watching (`--watch-namespaces` / `WATCH_NAMESPACE`)
- Operator log level: the manager runs at `info`/JSON by default (`zap.Options{Development: false}` in `cmd/main.go`). Configurable via the chart's `logging.level` / `logging.development` / `logging.encoder` values → `--zap-log-level` / `--zap-devel` / `--zap-encoder`, plus a generic `extraArgs` escape hatch. Note `debug` (or `level: 1`) re-enables the operator's own V(1) per-reconcile lines, ~100/hour per instance
- Pass-through endpoints: `spec.passThroughEndpoints` proxies arbitrary API requests to upstream services with path, target, auth, forwardHeaders, includeSubpath, methods, static headers, secret-backed headers (via `headerSecrets` with prefix), and default query params — written to `general_settings.pass_through_endpoints`; secret headers injected as `PASSTHROUGH_{PATH}_{HEADER}` env vars
- Enterprise license management: convention-based Secret detection (`{instance}-license` or `litellm-license`), `LITELLM_LICENSE` env var injection via `secretKeyRef`, `.status.license` reporting, Secret watches for automatic reconciliation, `EnterpriseLicenseRequired` condition on downstream controllers for enterprise-only API errors
- JWT authentication (enterprise): `spec.jwtAuth` with `enable_jwt_auth` + `litellm_jwtauth` in `general_settings`; **token-validation env vars** `publicKeyUrl`/`issuer`/`audience` → `JWT_PUBLIC_KEY_URL`/`JWT_ISSUER`/`JWT_AUDIENCE` on the proxy Deployment (the proxy reads these from the environment, not from config — without `publicKeyUrl` no token can be validated) — all claim field mappings (`adminJwtScope`, `adminAllowedRoutes`, `teamIdJwtField`, `teamIdsJwtField`, `orgIdJwtField`, `userIdJwtField`, `userEmailJwtField`, `userRoleJwtField`, `endUserIdJwtField`, `userIdUpsert`), `publicKeyTtl`, `scopeModelMappings` for fine-grained model access control; **JWT role-based RBAC** (`userRolesJwtField`, `userAllowedRoles`, `enforceRbac` under `litellm_jwtauth`, `objectIdJwtField`) which feeds the caller's JWT roles into `spec.rbac.rolePermissions` for per-role model access; **full `litellm_jwtauth` surface** — team/org alias lookup (`teamAliasJwtField`/`orgAliasJwtField`), `teamIdDefault`, `teamAllowedRoutes`, `teamIdUpsert`, `teamClaimFallback`, `userAllowedEmailDomain`, `enforceTeamBasedModelAccess`, `enforceScopeBasedAccess`, `syncUserRoleAndTeams`, `rolesJwtField`, structured `scopeMappings`/`roleMappings`/`jwtLitellmRoleMap`/`routingOverrides`, OIDC UserInfo (`oidcUserinfo*`), virtual-key mapping (`virtualKeyClaimField`/`virtualKeyMappingCacheTtl`), and `customValidate` (baked-image handler). Note: `scopeModelMappings` (map) is rendered into `scope_mappings` (the list LiteLLM actually reads — the old `scope_model_mappings` key was a no-op). `EnterpriseFeaturesConfigured` warning condition when enabled without license
- OAuth2 authentication (enterprise): `spec.oauth2Auth` with `enable_oauth2_auth` + `oauth2_config_mappings` in `general_settings` — named mappings from JWT fields to LiteLLM attributes (e.g., `client_id` → `team_id`) for machine-to-machine auth; `EnterpriseFeaturesConfigured` warning condition when enabled without license
- External secret manager integration: `spec.secretManager` configures LiteLLM's native secret manager support — 6 providers (`aws_secret_manager`, `aws_kms`, `azure_key_vault`, `google_secret_manager`, `google_kms`, `hashicorp_vault`); `key_management_system` and `key_management_settings` written to `general_settings` in `proxy_server_config.yaml`; provider credentials injected via `envFrom` from a referenced Secret; provider-specific env vars (AWS region/role, Azure vault URI/tenant, Vault address/namespace/auth/mount/prefix); AWS IRSA support via `webIdentityTokenPath`; `.status.secretManager` with `configured` and `provider` fields; credentials Secret validation with warning events
- Instance-level logging controls: `spec.logging` with `auditLogs` (`store_audit_logs` + `audit_log_retention_days`), `turnOffMessageLogging`, `redactUserApiKeyInfo`, `spendLogRetention` (`maximum_spend_logs_retention_period` + `maximum_spend_logs_retention_interval`) — all written to `general_settings` / `litellm_settings` in the generated `proxy_server_config.yaml`
- Admin UI management: `spec.adminUI` with `disabled` (DISABLE_ADMIN_UI env var), `adminOnly` (`ui_access_mode: "admin_only"` in general_settings), `storeModelInDB` (`store_model_in_db` in general_settings), `defaultTeamDisabled` (`default_team_disabled` in general_settings), `apiDocBaseURL` (LITELLM_UI_API_DOC_BASE_URL env var), `docsURL` (DOCS_URL env var), `rootRedirectURL` (ROOT_REDIRECT_URL env var), `logoURL` (UI_LOGO_PATH env var), `emailLogoURL` (EMAIL_LOGO_URL env var), `emailSupportContact` (EMAIL_SUPPORT_CONTACT env var), `colorThemeConfigMapRef` (mounts `enterprise_colors.json` from a ConfigMap at `/app/enterprise/enterprise_ui/enterprise_colors.json` via subPath)

#### LiteLLMUser (user management via API)

- CRUD via LiteLLM REST API (`/user/new`, `/user/update`, `/user/delete`, `/user/info`)
- Fields: userId, userEmail, userRole (proxy_admin/proxy_admin_viewer/internal_user/internal_user_viewer), maxBudget, budgetDuration, models, tpmLimit, rpmLimit, metadata, **blocked** (disable all user requests), **softBudget**, **modelRpmLimit**/**modelTpmLimit**, **objectPermission**
- Team associations with cross-CR reference resolution (teamRef -> status.litellmTeamId)
- Requeues if referenced team not yet synced
- **initialPasswordSecretRef**: initial Admin UI password from a Secret key. Applied via `POST /user/update` (current LiteLLM rejects `password` on `/user/new`) once after create/adopt, then only when the Secret's value changes — never on resync, so a user's own password change sticks. Change detection via an Argon2id PHC digest in `status.initialPasswordDigest` (fixed OWASP params m=19MiB,t=2,p=1; a digest with other params never matches, so crafted status cannot force huge allocations; do not pre-hash with SHA-256 — CodeQL go/weak-sensitive-data-hashing), persisted with a status merge patch right after applying. Secret watch enqueues referencing users. Reported on a separate `InitialPasswordApplied` condition (not `Synced`). `Users().SetPassword` redacts the password from API error bodies (validation errors echo input)

#### LiteLLMCredential (reusable provider credentials, DB-backed via /credentials API)

- API-backed resource (as of v0.11.3): the credential controller calls `POST` / `PATCH` / `DELETE` on `/credentials/{credential_name}`. LiteLLM stores the values in its DB (encrypted at rest using `LITELLM_SALT_KEY`) and merges them into models that reference the credential by name. Credentials are visible in the Admin UI's Credentials tab.
- Fields: `instanceRef`, `credentialName` (sent as `credential_name` to LiteLLM), `apiKeySecretRef`, optional `apiBase` / `apiVersion`, free-form `params` map (`map[string]JSON` — arbitrary JSON values, e.g. Vertex SA JSON) merged into `credential_values` (reserved keys `api_key`, `api_base`, `api_version` cannot be overridden by params). Each entry's `credential_info` is set to `{ managed_by: "litellm-operator" }` so it's distinguishable in the UI from manually-created credentials
- Wire format: `{credential_name, credential_values: {api_key, api_base, api_version, ...params}, credential_info: {managed_by: "litellm-operator"}}`. The operator reads the Secret value at reconcile time and sends it directly to LiteLLM — there is no `CREDENTIAL_*_API_KEY` env var on the proxy Deployment anymore
- Sync model: a SHA256 hash of `(spec + secret-value)` is stored on the CR's `litellm.palena.ai/sync-hash` annotation. On reconcile, if the hash matches the stored one, the controller is a no-op. If it differs, the controller `PATCH`es `/credentials/{name}` (falling back to `POST` create on 404). Periodic resync every 5 minutes as a safety net for missed watch events
- **Secret rotation propagates in seconds**: the controller watches `corev1.Secret` and enqueues every `LiteLLMCredential` whose `apiKeySecretRef.name` matches the changed Secret. No proxy pod restart is required — DB credentials are resolved on each request
- Cross-CRD: `LiteLLMModel.spec.litellmParams.credentialRef` resolves to `credentialName` and is sent to `/model/new` as `litellm_credential_name`. LiteLLM merges the DB credential into the model's `litellm_params` at request time. Models registered via API now correctly receive `api_base` / `api_version` / `api_key` from their referenced credential — this is what makes Azure OpenAI / Azure AI Foundry models work
- Deletion: finalizer calls `DELETE /credentials/{name}` (best-effort — the DB credential is orphaned, not blocking, if the instance is unreachable). LiteLLM's DELETE is idempotent, so re-deletion after a successful one is a no-op
- `.status.configured` reflects whether the credential is registered in the DB; `.status.referencedByModels` counts CRs using `credentialRef`; `Ready=True` with `reason=Synced` means the credential is live in LiteLLM
- Migration from v0.11.2: `credential_list` is no longer rendered into `proxy_server_config.yaml`. On upgrade, the first reconcile after pod start registers each existing `LiteLLMCredential` against `/credentials`. The proxy rolls once (because the dropped `credential_list` section changes the ConfigMap hash) and then credentials are DB-backed

#### LiteLLMGuardrail (content moderation / safety integrations, config-level)

- Config-level resource: the guardrail controller only validates the CR (instance exists, API key Secret exists and has the requested key if declared). Actual materialization happens in the instance controller when it rebuilds the ConfigMap + Deployment
- Supported providers: `aporia`, `lakera`, `bedrock`, `presidio`, `guardrails_ai`, `azure`, `llm_guard`, `llamaguard`, `google_text_moderation`, `custom_guardrail` (enum-validated)
- Execution modes: `pre_call`, `post_call`, `during_call`, `logging_only` (enum-validated)
- Fields: `instanceRef`, `guardrailName` (used as the `guardrail_name` in the rendered list), `provider`, `mode`, optional `apiKeySecretRef`, optional `apiBase`, optional `defaultOn`, free-form `params` map (`map[string]JSON` — arbitrary JSON values, e.g. Presidio `pii_entities_config`) merged into `litellm_params` (reserved keys `guardrail`, `mode`, `api_key`, `api_base`, `default_on` cannot be overridden), and arbitrary `envVars` list for provider-specific env vars (e.g., AWS_REGION for bedrock)
- API key is injected into the proxy pod via a `secretKeyRef`-backed env var named `GUARDRAIL_{GUARDRAIL_NAME}_API_KEY` (same sanitization regex as credentials/pass-through) and referenced from the `guardrails` list as `os.environ/…` — the operator never reads the secret value. Guardrails without an `apiKeySecretRef` (e.g. local presidio, internal custom_guardrail) skip env var injection and the `api_key` field entirely
- Rendered into the top-level `guardrails` list in `proxy_server_config.yaml` — each entry has `guardrail_name` plus a `litellm_params` map with `guardrail: <provider>`, `mode`, and optional `api_key: os.environ/GUARDRAIL_{NAME}_API_KEY`, `api_base`, `default_on`, and the provider-specific `params`
- Instance controller watches `LiteLLMGuardrail` CRs and reconciles the owning instance on create/update/delete; additionally filters out guardrails whose `instanceRef` points to a different instance, and guardrails already marked for deletion (they stay listable until the finalizer is removed, and rendering one would put it back into the config for a reconcile). Because the guardrail list only reaches the proxy through the ConfigMap, deletion depends on the pod-template config digest to actually roll — see `litellm.palena.ai/config-hash` above
- Per-key/per-team opt-in: `LiteLLMVirtualKey.spec.guardrails` and `LiteLLMTeam.spec.guardrails` are forwarded to `/key/generate`, `/key/update`, `/team/new`, `/team/update` as the `guardrails` JSON field. This requires a LiteLLM Enterprise license — the downstream controllers report `EnterpriseLicenseRequired` if LiteLLM rejects the call
- `.status.configured`, `.status.lastSyncTime`, and `Ready` condition reflect validation state (`InstanceNotFound`, `SecretNotFound`, `SecretKeyMissing`, or `Validated`); 5-minute periodic resync

#### LiteLLMBudget (reusable budget / rate-limit tier via API)

- CRUD via LiteLLM REST API (`/budget/new`, `/budget/update`, `/budget/info`, `/budget/delete`). Short name `lb`

#### Bidirectional config sync (separate controller)

- Dedicated `ConfigSync` controller watches `LiteLLMInstance` resources with `spec.configSync.enabled: true`
- Runs on configurable interval (default 30s) — compares CRD state with LiteLLM API state across all 6 API-managed resource types (models, teams, users, keys, organizations, customers)
- Drift detection: compares key fields of CRD spec against API response. When drift is found, applies `conflictResolution` policy:
  - `crd-wins` (default): clears the sync hash annotation on the drifted CRD, triggering the per-resource controller to re-push CRD state
  - `api-wins`: reports drift via events, preserves API state
  - `manual`: reports drift, requires manual resolution
- Deleted-from-API detection: when a managed CRD's API resource is missing, clears the status ID and sync hash so the per-resource controller recreates it (crd-wins) or reports the issue (api-wins/manual)
- Unmanaged resource handling via `unmanagedResourcePolicy`:
  - `preserve` (default): counts and ignores API resources with no matching CRD
  - `prune`: deletes unmanaged API resources
  - `adopt`: counts and reports via events
- Audit events: emits Kubernetes Events on the instance for drift, pruning, recreation, and unmanaged resource detection (when `auditChanges: true`; prune/recreate events always emitted)
- Status reporting: populates `status.configSync` with per-resource-type synced/unmanaged counts, last sync time, and sync errors
- Sets `ConfigSynced` condition on the instance (True/False with reason)
- Complementary to per-resource controllers: per-resource controllers handle real-time CRD lifecycle (event-driven); config sync provides periodic comprehensive drift detection, unmanaged resource handling, and status aggregation
